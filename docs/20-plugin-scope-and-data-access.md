# 20 · 插件作用域与数据可达

> 本文修正 [18-agent-and-memory](18-agent-and-memory.md) §7 的一处设计：
> 「插件不绑定智能体」这句话**只对了一半** ——
> 插件**代码**不绑定智能体，但插件的**启用与授权**必须绑定。

---

## 1. 两个被指出的问题

### 1.1 跨智能体读数据不是「越界」，是「要讲清楚」

上一版设计里，我把 `data.query` 的行级过滤定成"强制只能读当前智能体"，
理由是"防止跨智能体读到别人的对话"。

**这个定性是错的。** 跨智能体读取不是安全漏洞，而是**一种需要用户知情的更大权限**：

- 用户自己想要「这个角色知道我和别的角色聊过什么」是完全合理的需求
- 想把三个角色的记忆打通、做统一摘要，是正经功能，不是攻击
- 把它一律堵死，等于用"做不到"代替"问一声"

正确的做法是**给它一个独立权限 + 一句说清楚的话**：

```
data.read.crossAgent
  提示：插件会访问除插件安装的智能体外其他智能体的信息
```

不声明这个权限 → 只能读自己那个智能体的数据（fail-closed）。
声明了 → 用户在授权时看到上面那句话，自己决定。

> **平台该做的是"让用户知情"，不是"替用户决定"。**
> 把合理需求堵死，用户不会觉得安全，只会觉得这平台没法用。

### 1.2 现状：插件是纯全局的

代码事实：

```dart
// PluginHost
_rootDir = p.join(docs.path, 'plugins');           // 一份代码，全局
String _enabledKey(String pluginId) =>
    'plugin.enabled.$pluginId';                     // 键里没有智能体

// Gatekeeper
final Map<String, Set<String>> _declared;          // 按 pluginId
final Map<String, Set<String>> _granted;
```

所以今天：装一个插件 = 对所有智能体生效；关掉它 = 对所有智能体关掉；
授权一次 = 对所有智能体授权。

这有三个具体问题：

1. **用户想给角色 A 装"心情面板"，不想让角色 B 也有** —— 做不到
2. **给 A 授权了"读记忆"，B 白拿** —— 用户从没为 B 同意过
3. **跨智能体权限没有落脚点** —— "除安装它的智能体之外"这句话里，
   首先得有"它装在哪个智能体上"

## 2. 三层拆分：安装 / 启用 / 授权

```
① 安装（全局，一份代码）
   <app>/plugins/<pluginId>/
   └─ 磁盘上只有一份。装两次不会有两份代码。

② 启用（多对多：插件 × 智能体）
   (pluginId, agentId, enabled)
   └─ "这个插件为这个智能体工作"

③ 授权（跟着②走）
   (pluginId, agentId) → 权限集
   └─ 用户为"这个插件服务这个智能体"这件事授权的
```

**为什么授权要跟着启用走**：

用户给角色 A 授权"读记忆"，和为角色 B 授权，是**两次不同的决定** ——
A 和 B 是两个不同的关系。按插件授权的话，B 会白拿 A 的授权。

**但这里有个摩擦**：装一个插件、为 3 个智能体启用 → 问 3 次。

缓解（不是绕过）：

- 安装时展示**完整权限清单**（"这个插件一共会要这些"），用户先有个预期
- 为某个智能体启用时，只问**这个智能体特有的**决定
- **危险权限每次都问**（`data.read.crossAgent` / `fs.write` / `net` / `model.chat`）
- 提供一个「对之后新建的智能体也这样」的勾选 —— 把 N 次变成 1 次 + 1 个勾

### 2.1 不是所有插件都需要智能体

主题包、独立工具页这类东西本来就没有"属于哪个智能体"的概念。

manifest 加一个可选字段：

```jsonc
{
  // agent  —— 需要为智能体启用（工具、插槽 UI）。**默认值。**
  // global —— 全局启用一次（主题、独立页面）
  // both   —— 都行
  "scope": "agent"
}
```

**默认 `agent`**：更安全，也更符合"智能体是核心单位"。
全局启用的插件读不到任何"自己的"智能体数据（见 §4 的 fail-closed 规则）。

## 3. 关键工程权衡：运行时实例

这是整个设计里**唯一需要真正拍板**的地方。

### 3.1 两种做法

| | 一个插件一个运行时 | 一个 (插件, 智能体) 一个运行时 |
|---|---|---|
| WebView 数 | N 个插件 | N × M 个（插件 × 启用的智能体） |
| 内存 | 省 | 费（Android WebView 空页约 15–25 MB） |
| 状态隔离 | **插件自己负责** | **宿主保证** |
| 插件写法 | 必须处处按 agentId 分区 | 就是个普通单实例插件 |

### 3.2 为什么必须选后者

看我们自己的演示插件：

```js
// plugins/rock-paper-scissors/index.js
let score = { user: 0, ai: 0, draws: 0, rounds: 0 };
```

**这是模块级状态。** 如果同一个运行时同时服务角色 A 和角色 B，
两个人玩石头剪刀布会**共用同一个比分**。

这不是理论问题 —— 它是"一个运行时服务多个智能体"这个方案下**必然出现**的错误，
而且**插件作者不会意识到**（他写的是单实例代码）。

> 状态隔离如果交给插件作者，就一定有人忘。
> 而忘了的后果是**跨智能体的数据串台** —— 正是我们最不想出的那类事故。

**所以：默认由宿主保证隔离，一个 (插件, 智能体) 一个运行时。**

### 3.3 代价与缓解

内存是真实成本。缓解手段：

1. **按需创建** —— 用户进到某个智能体的界面时才创建它的运行时，
   不是把所有启用过的都提前拉起来
2. **并发上限 + LRU 挂起** —— 同时活跃上限 3–4 个，超出的销毁 WebView
3. **挂起是安全的**，因为下方这条规范

### 3.4 由此产生的插件规范（重要）

> **运行时可能被随时回收。插件的重要状态必须落库（`state.set`），
> 不能只放在 JS 内存里。**

这不是新的限制，是**宿主给出的承诺**：

- 你被回收了，下次启动时 `state.get` 能拿回你存的东西
- 你不用管自己什么时候被回收

对 `rock-paper-scissors` 来说，就是把 `score` 从模块变量改成
每次 `state.get` / `state.set`。**这本来就是它该有的写法** ——
今天它把比分放内存里，用户切出去再回来比分就没了。

### 3.5 给"纯函数式插件"留的优化口

有些插件确实是纯的（翻译按钮、格式化工具），不持有跨调用状态。
让它们也占一个 WebView 是浪费。

manifest 可选声明：

```jsonc
{ "stateless": true }
```

宿主对这类插件**可以共享运行时**。

**默认 false（也就是分开）** —— 把选择权交给作者，
但默认选安全的那一边。声明 `stateless: true` 是作者明确说
"我没有跨调用状态"，说错了是他的 bug，而且影响面只在他自己。

## 4. 数据可达：`data.*` 查询 DSL

### 4.1 为什么不给 SQL

给 SQL 看起来最自由，但同时破坏四件事：

1. **schema 变成对外契约** —— 以后改表就是破坏性变更
2. **行级权限无处施加** —— `SELECT * FROM messages` 直接绕开授权
3. **没有成本边界** —— 一个没加索引的查询能卡死 App
4. **审计粒度丢失** —— 只能记"执行了一条 SQL"，记不了"读了谁的什么"

### 4.2 给什么

```js
await tsukiro.data.query({
  entity: 'message',            // agent | conversation | message | memory | provider
  where: { role: 'user' },      // 声明式条件，不是表达式
  order: 'createdAt.desc',
  limit: 50,                    // 有上限，超了夹取
  select: ['id', 'content', 'createdAt'],
});
```

宿主负责：把 `where` 翻成 SQL、**注入作用域过滤**、夹 limit、写审计。

### 4.3 作用域过滤规则（fail-closed）

每次调用都带一个由**宿主注入**的 `agentId`（插件不能伪造，见 §5）。
按权限决定过滤范围：

| 插件声明的权限 | `where` 里注入的额外条件 |
|---|---|
| 只有 `data.read` | `agent_id = <本次调用的 agentId>` |
| 有 `data.read.crossAgent` | **不加过滤**（可跨智能体） |
| 两者都没有 | 拒绝 |
| `agentId == null`（全局上下文）且只有 `data.read` | **返回空**（全局上下文没有"自己的"数据） |

最后一行是 fail-closed 的关键：全局启用的主题包拿不到任何智能体数据。

### 4.4 为什么这比 SQL 更自由，而不是更受限

- 插件**够得着**所有实体（今天连读都读不到）
- 插件**不用关心 schema 演进** —— 宿主可以加列、换存储（SQLite → 服务端），插件一行不改

> SQL 给的是"今天的自由度"；
> DSL 给的是"**不会因为宿主升级而失效**的自由度"。
> 后者才是真自由 —— 你的代码不会因为宿主改表而坏掉。

## 5. 作用域身份：怎么让下游都不用改

门禁、工具表、插槽表现在都以 `pluginId` 为键。改成按 (插件, 智能体) 之后，
如果每个表都改成复合键，改动会散到十几处。

**做法：宿主生成一个「作用域身份」字符串，下游全用它。**

```
scopedId = "<pluginId>@<agentId>"        // 智能体作用域
scopedId = "<pluginId>@*"                // 全局作用域
```

于是：

- `Gatekeeper.registerPlugin(scopedId, declared)` —— **一行不用改**
- `ToolRegistry.registerPlugin(...)` 同理
- `SlotRegistry` 同理
- `BridgeSession` 加一个宿主绑定的 `agentId` 字段

`agentId` 和 `pluginId` 一样，**由宿主在创建会话时绑定，不信任消息里的自称**
（与 docs/07 的实例绑定同一原则）。

这样"插件 A 服务智能体 X"和"插件 A 服务智能体 Y"在宿主看来是两个不同的
注册主体，各自有独立的权限、工具、插槽 —— 而内核一行不改。

## 6. 数据模型

```sql
-- 安装：全局一份
CREATE TABLE plugin_installs (
  plugin_id    TEXT PRIMARY KEY,
  version      TEXT NOT NULL,
  directory    TEXT NOT NULL,
  installed_at INTEGER NOT NULL
);

-- 启用 + 授权：按 (插件, 智能体)
CREATE TABLE plugin_activations (
  plugin_id    TEXT NOT NULL,
  agent_id     TEXT NOT NULL,          -- '*' 表示全局启用
  enabled      INTEGER NOT NULL DEFAULT 1,
  -- 授权集。JSON 数组。**按激活存，不是按插件存** ——
  -- 给角色 A 读记忆的授权不该自动给角色 B
  granted      TEXT NOT NULL DEFAULT '[]',
  activated_at INTEGER NOT NULL,
  PRIMARY KEY (plugin_id, agent_id)
);

-- 插件状态也按 (插件, 智能体) 分区
-- （今天 _stateKey 只有 pluginId，跨智能体会串）
-- plugin.state.<pluginId>.<agentId>.<key>
```

**迁移**：现有 `plugin.enabled.<pluginId>` → 展开成
`plugin_activations(plugin_id, '*', enabled)`。
旧数据是全局的，就迁成全局启用，语义不变。

## 7. 权限目录新增

```dart
'data.read': PermissionSpec(
  'data.read',
  PermissionLevel.install,
  '读取本智能体的对话、记忆与配置',
),
'data.read.crossAgent': PermissionSpec(
  'data.read.crossAgent',
  // 用用户原话 —— 这句话是给用户看的，就该按用户能懂的方式写
  PermissionLevel.confirm,
  '插件会访问除插件安装的智能体外其他智能体的信息',
),
'data.write': PermissionSpec(
  'data.write',
  PermissionLevel.confirm,
  '修改本智能体的对话与记忆',
),
```

两条设计点：

- `data.read.crossAgent` 是 **`confirm` 级**（不是 `install` 级）——
  它每次都要用户当场确认，不能"装的时候一并同意"
- 描述文案**用用户能懂的话**，不用 "cross-agent data access" 这种术语

## 8. 对 docs/18 §7 的修订

原文：

> | 插件**不绑定**智能体 | 插件是全局安装的，智能体是用户创建的，两者不是从属关系 |

改成：

> | 插件**代码**不绑定智能体 | 一份代码，装在 `<app>/plugins/` |
> | 插件**启用与授权**绑定智能体 | 同一个插件可以为多个智能体分别启用，各自独立授权 |
> | 插件可以是全局的 | 主题包、独立页面这类没有"属于谁"的概念，声明 `scope: global` |

**原来那句话的洞见仍然成立**：插件和智能体不是**从属**关系（不是"插件的子对象"），
而是**多对多的激活**关系。这才是准确的说法。

## 9. 落地步骤

| # | 内容 | 判据 |
|---|---|---|
| 1 | `plugin_activations` 表 + 迁移 | 现有插件迁成全局启用，行为不变 |
| 2 | `scopedId` 贯通门禁/工具表/插槽表 | 同一插件对两个智能体有两个独立注册主体 |
| 3 | 运行时按激活创建（按需 + LRU） | 只给当前打开的智能体起 WebView |
| 4 | `data.read` / `data.read.crossAgent` + `data.query` | 插件能读最近 20 条消息；不声明 crossAgent 时读不到别的智能体 |
| 5 | 启用/授权 UI | 为单个智能体启停插件；危险权限当场确认 |
| 6 | `state.*` 按 (插件, 智能体) 分区 | 两个智能体的插件状态互不串 |

**第 5 步之前，第 4 步无法验证** —— 没有 per-agent 启用，
crossAgent 的"除安装它的智能体之外"就无从谈起。

所以顺序上 **1 → 2 → 5 → 4** 比 **1 → 2 → 3 → 4 → 5** 更顺：
先把"能按智能体启停"做出来（5 可以先用最简单的 UI），
再验证数据作用域（4）。

---

## 10. 一句话总结

**插件代码装一份，启用和授权按智能体各来一次；
默认只能读自己的数据，想读别人的要单独声明并当场确认 ——
而"别人的"这句话，只有在插件真的属于某个智能体之后才有意义。**
