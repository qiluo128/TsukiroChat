# 23 · Surface 嵌入与视觉能力路线

> 本文定的是**实现顺序与取舍**，不是"该不该做"。
> 用户已明确：Surface 与 Web 嵌入 UI **是当支持的** ——
> 某些特殊需求只能靠它（现成的 Web 前端、复杂的自有交互）。
>
> 上一轮我把「能不能做」和「默认该用哪条路」混在一句话说，
> 那是不对的。本文分开。

---

## 1. 先纠正一个说法

我上轮说「不建议做 surface 嵌入节点」，理由里混了三件事：

| 我混在一起的 | 实际是 |
|---|---|
| 平台视图不能毛玻璃 | **是真的**，但只是"这一条路的代价" |
| 建议默认用原生节点 | 是**默认策略**，不是"不该有这个能力" |
| 所以别做这个节点 | **错的推论** |

**能力该有。** 就像 WebView 本身也不是"默认选择"，但没有它就没有
一整个插件品类。

正确的说法是：

> **平台视图嵌入是"有明确代价的能力"，该做，但要把代价讲清楚，
> 并且让它在需要时才用。**

---

## 2. 嵌入有两条路，代价完全不同

这是整个计划的**技术核心**，先说清楚再排期。

| | **A. 平台视图嵌入**（真 WebView / 真 Flame） | **B. 原生节点扩展**（Flutter 自己画） |
|---|---|---|
| 能做什么 | 现成 HTML/JS、复杂自有交互、真游戏 | 粒子、模糊、变换、着色器 |
| 圆角裁剪 | ⚠️ 受限（iOS 可以，Android 差） | ✅ |
| 阴影 / 描边 | ❌ 多数做不到 | ✅ |
| **被毛玻璃模糊** | ❌ **不可能** | ✅ |
| 与 Flutter 手势共存 | ⚠️ 要 workaround | ✅ |
| 深浅色主题 | ❌ 插件自己管 | ✅ 自动 |
| 性能 | 一个 WebView 15–25MB | 可忽略 |

**关键结论：两者不是替代关系，是分工。**

- 想要**"和周围融为一体"** → B
- 想要**"插件自带的完整交互"** → A

---

## 3. 路线图

### 阶段 1 · 原生节点扩展（先行）

**为什么先做它**：便宜、无平台风险、立刻改善观感，而且是 B 路的基础。

| # | 节点 | 用途 | 成本 |
|---|---|---|---|
| 1.1 | `blur` | 毛玻璃卡片、背景虚化 | 小 |
| 1.2 | `transform` | 旋转/缩放/位移 —— **物理瓶的倾斜就靠它** | 小 |
| 1.3 | `stack` | 叠放（毛玻璃垫在图片上必需） | 小 |
| 1.4 | `particle` | 火焰/星光/落樱 | 中 |
| 1.5 | `gradient` | 原生渐变（现在只能靠背景设置） | 小 |

**验收判据**：礼物展柜能做出「图片卡片 + 毛玻璃标题条」这种效果。

### 阶段 2 · Surface 嵌入节点（`surface`）

**这是用户明确要求的那一项。**

```jsonc
{
  "type": "surface",
  "surfaceId": "mini-game",   // 指向插件自己的 surfaces 声明
  "height": 320,              // 给个高度，不要让它无限撑开
  "clip": "rounded",          // 圆角裁剪（能裁就裁，裁不了要如实降级）
  "placeholder": { "type": "text", "text": "游戏加载中…" }
}
```

要解决的问题（按麻烦程度排）：

| # | 问题 | 处理方式 |
|---|---|---|
| 2.1 | **生命周期** | 嵌进列表里会随滚动反复创建/销毁 —— 必须做**实例缓存**，不能每次重建 WebView |
| 2.2 | **滚动与手势** | 平台视图会吃掉滚动。要么限制它在不滚动的区域，要么给它 `interaction: 'none' \| 'tap' \| 'full'` |
| 2.3 | **尺寸** | 必须给高度（平台视图测量和 Flutter 布局不同步） |
| 2.4 | **视觉降级要如实** | 裁不了圆角时**不要假装裁了** —— 渲染成方角并记一条日志 |
| 2.5 | 状态同步 | 复用现有 `surface.update` / `surface.event` |

**2.1 是真正的难点。** 一个 WebView 实例 15–25MB，礼物展柜里有 6 张卡片
各嵌一个 → 150MB，而且滚动时反复销毁重建会闪。

做法：**每个 (插件, surfaceId) 一个实例，被移出屏幕时不销毁、只 detach**，
用一个小的池子（上限 2–3 个活跃）。这和 docs/20 里"实例池"的思路一致。

### 阶段 3 · `motion.*` 原语（与渲染解耦）

物理瓶需要倾角，但 `motion` 是**独立能力**，不该和渲染绑在一起。

```
motion.orientation    倾角（pitch/roll/yaw）
motion.accelerometer  加速度
motion.shake          摇一摇（**语义化事件**，不是原始数据）
```

**`motion.shake` 这种语义化事件特别值得做** ——
插件真正想要的是"用户摇了一下"，不是 60fps 的加速度数组。

Android 侧的真问题（要单独想清楚）：
- 传感器是**前台监听**还是后台？后台耗电怎么算？
- 用户怎么知道某个插件在持续读传感器？（要有可见指示）
- 多个插件同时要传感器时，是共享一个监听还是各来一份？

### 阶段 4 · 物理瓶（验证整条链路）

它同时用到 `motion.orientation` + `transform`，是**最好的集成测试**。

优先用 **阶段 1 的 `transform`** 实现（全原生、能毛玻璃、省电），
`kind: flame` Surface 作为备选（需要更强物理时）。

---

## 4. 一个必须写下来的取舍

`surface` 嵌入节点做出来之后，**插件作者会想用它做一切**——
因为"我熟悉的 HTML"最省事。但那会让界面变丑、变慢、主题接不上。

所以除了做能力，还要做**引导**：

| 手段 | 说明 |
|---|---|
| 插件管理页标注 | 用了嵌入 Surface 的插件显示"包含自绘界面" |
| `surface.list` 自省 | 让插件知道有哪些声明过的 surface 可嵌 |
| 文档明写代价 | 不写"不支持"，写"这样做会失去什么" |

**不阻止，但要让选择是知情的。**

---

## 5. 排期建议

| 顺序 | 内容 | 依赖 |
|---|---|---|
| 1 | 阶段 1.1–1.3（`blur` / `transform` / `stack`） | 无 |
| 2 | 阶段 2（`surface` 嵌入节点 + 实例池） | 用户明确要求，优先 |
| 3 | 阶段 1.4–1.5（`particle` / `gradient`） | 无 |
| 4 | 阶段 3（`motion.*`） | 需要 Android 侧设计 |
| 5 | 阶段 4（物理瓶演示） | 3 |

**阶段 2 提前到第 2 位**，因为它是用户点名要的，而且 2.1（实例池）
是个会反复出现的基础设施 —— 早做早受益。
