# 27 · 权限授予策略 + 逐智能体的工具配置

> 状态：设计讨论，**未实现**。
> 相关：`docs/06-permissions.md`、`docs/26-per-agent-scope.md`

---

## 1. 用户的重新设计

### 安装插件时

弹「敏感权限提示窗」，对每个敏感权限选：

```
始终允许   →  授予，之后不再问
使用询问   →  授予，但每次用到时问
不安装此插件 → 放弃整个插件
```

**「使用询问」= 现有的 `confirm` 级**（每次确认、永不"不再询问"）。

### 调用时

「使用询问」的权限在 **tool 被调用时**弹框，其他级别不弹。

### 智能体设置界面

两个页：**插件** / **工具**。

- **工具页**：配置这个智能体可用的**系统提供的 tools**
  （时间、定位、相册、工作区读写…），敏感工具同样有提示窗。
- **插件页**：用户自己说"没太想好"。

---

## 2. 映射到现有概念

| 用户的新说法 | 现有 | 差异 |
|---|---|---|
| 始终允许 | `PermissionLevel.install` + granted | 无 |
| 使用询问 | `PermissionLevel.confirm` + granted | 无 |
| 不安装此插件 | 不 grant + 中止安装 | 需要"中止安装"的能力（现在只是记录错误） |
| ~~宿主保留~~ | `PermissionLevel.denied` | 新设计里这一级**从用户视角消失**（用户只能在"询问"和"不装"之间选） |

**权限目录要分两类：**

- **可配置级**（`install` / `confirm`）：展示在安装弹窗里，让用户选
- **宿主保留**（`denied`）：**不进安装弹窗**，直接导致安装失败
  （现在哪些属于这类？`docs/06` 里列的无障碍/录屏/发短信）

## 3. 两个会立刻出问题的地方（必须先解决）

### ① `visibleTools` 会把 confirm 级的工具**隐藏掉**

```dart
// tool_registry.dart
for (final perm in tool.permissions) {
  if (!gatekeeper.check(tool.pluginId, perm).isAllowed) {   // ← confirmRequired 时 isAllowed == false
    permissionOk = false;
    break;
  }
}
if (!permissionOk) continue;
```

**后果**：如果给「定位」工具声明 `location`（confirm 级），
它会从工具表里**消失** —— 用户永远看不到它，也永远不会被询问。

**必须改**：`confirmRequired` 应该是**可见但需要确认**，不是"不可见"。

判据：`check` 的三种结果是 `allow` / `confirmRequired` / 拒绝。
**只有"拒绝"才该隐藏**。

### ② `gatekeeper.check` 是**同步**的，而"调用时询问"必须**异步**

现状：

```dart
GateResult check(String pluginId, String? permission);   // 纯同步，无 UI
```

它只回答"该不该问"，**没有人去问**。所以现在 `confirm` 级是个
**只判不执行的空洞** —— 这正是为什么 `confirm` 级从来没真正生效过。

要落地「使用询问」必须加一个异步执行器：

```dart
abstract class ConfirmationBroker {
  /// 弹原生确认框并等用户决定。
  /// 返回 true = 允许这一次。
  Future<bool> ask({
    required String title,        // 「允许 时间插件 读取你的位置吗？」
    required String permission,
    required String pluginId,
    String? reason,               // 插件声明的申请理由
  });
}
```

调用链上每一处遇到 `confirmRequired` 都要 await 它：

```
原语调用 / 工具调用
  → gatekeeper.check() → confirmRequired
  → await broker.ask(...)
  → true  → 继续
  → false → 返回 USER_CANCELLED
```

**这是「使用询问」的全部工程量所在**，比权限目录本身大得多。

## 4. 「插件的部分没想好」—— 我的建议：**不要单独做逐智能体插件页**

理由：

> **插件是「装载单位」，工具是「能力单位」。**
> 用户真正想控制的是"这个智能体能做什么"，而他能感知的形态只有工具。

所以：

```
插件页（全局，一次性）
  装 / 卸 / 启用停用 / 权限授予
  ※ 这里是"这台设备上装了哪些插件"

智能体 · 工具页（逐智能体）
  按插件分组显示所有可用工具
    ▾ 时间（宿主）            ☑ get_current_time
    ▾ 麦当劳 MCP             ☑ query_meals  ☑ submit_score …
    ▾ 礼物插件               ☐ send_gift
  → 勾选 = 这个智能体的模型能看到 / 能调用
```

**「智能体 · 工具页」按插件分组的全选/取消，就等价于"逐智能体插件启用"**（对工具这一面）。

这样不需要第二个界面，也不需要回答"插件逐智能体启用"的复杂语义。

### 但要留一个例外

带 **UI 贡献**或**钩子/后台行为**的插件，光屏蔽工具是不够的
（见 `docs/26` §2）。那些贡献的作用域：

| 贡献 | 作用域 |
|---|---|
| 工具 | 逐智能体 ✅ |
| UI（上下文带 agentId 的插槽） | 逐智能体 ✅ |
| UI（`home.*` / `settings.*`，无 agentId） | **只能全局** |
| 钩子 / 后台任务 | **全局**（除非做授权层） |

## 5. 一个用户没提但会撞到的问题

**逐智能体配置 + 「使用询问」= 用户会被反复问。**

```
智能体 A 开了定位工具（ask 级）
→ 每问一次位置就弹一次框
```

这是 `confirm` 的定义（永不"不再询问"），但**在逐智能体的语境下**，
用户的自然诉求会是"**在这个智能体上始终允许**"。

那是"把 ask 升级成 install，但只对这个 agent"。数据结构上可以统一：

```sql
-- 现有设想
agent_scope(agent_id, target, enabled)

-- 如果要支持"对这个 agent 始终允许"
agent_grant(agent_id, permission, decision)   -- 'always' | 'ask'
```

**建议先不做**，但要预留：`decision` 的默认值来自全局授予，
逐智能体只覆盖。否则将来加这个维度要改所有调用点。

## 6. 系统权限 ≠ 应用内权限（两层，不能混）

用户已经指出"抛开申请手机权限时的安卓弹窗"，这一点必须坚持：

```
第一层  我们的授予        install / ask / 拒绝      应用内弹窗
第二层  Android 运行时权限  定位 / 相册 / 通知       系统弹窗
```

**我们的体系不能替代系统权限，也不能假设系统权限已授予。**

所以每个系统工具必须处理三种情况，并且**把结果如实告诉模型**：

| 情况 | 应该返回 |
|---|---|
| 应用内未授予 | 工具不可见（或隐藏前先问） |
| 应用内授予、系统未授予 | 调用时触发系统弹窗；被拒 → 明确说明"用户拒绝了系统权限" |
| 系统拒绝且不再询问 | 明确说明"需要去设置里手动开启" |

**不能静默失败** —— 那会让模型反复重试同一个失败，用户看到的是"AI 很笨"。

## 7. 建议的实施顺序

| # | 做什么 | 依赖 | 说明 |
|---|---|---|---|
| **1** | **修 `visibleTools`**：confirm 级可见 | 无 | 否则一切 confirm 级的工具都永久不可见 |
| **2** | **`ConfirmationBroker`** + 接通工具/原语调用链 | 1 | 「使用询问」的整个工程量在这 |
| 3 | 权限目录分类（可配置 vs 宿主保留） | 2 | 数据整理 |
| 4 | 安装时的授予弹窗（始终允许/询问/不装） | 2、3 | 复用 broker 的 UI 组件 |
| **5** | **智能体 · 工具页**（按插件分组） | 1 | 用户最直接要的东西 |
| 6 | 系统工具：定位（`geolocator`）、相册（`photo_manager`） | 2 | 各自还有系统权限处理 |
| 7 | 逐智能体授予覆盖（agent_grant） | 2、5 | 先预留，后实现 |

**1 和 5 最值得先做**：一个是修 bug（否则 confirm 级工具全隐身），
一个是用户能立刻感知的功能。
