# 06 · 权限模型

> **一句话**：插件在 manifest 声明权限 → 宿主安装时一次性弹窗授权 → 运行时宿主侧校验 → 用户可随时撤销 → 所有调用记审计。

---

## 1. 三条设计原则

1. **宿主是唯一守门人**：校验发生在宿主进程，而非 WebView 内的接口注入。任何 JS 层的「删掉这个 API 就调不到」都是假安全。
2. **安装时一次性授权**：同意后运行时不再打扰。理由是陪伴类 App 的交互频次高，每次弹窗会毁掉体验。
3. **可撤销且立即生效**：撤销不需要重启 App，下一次调用就失败。

### 1.1 为什么不在 WebView 里做接口过滤

看似更省事的做法是「没授权的原语就不注入到 `tsukiro` 对象上」。但攻击者可以：

```js
// 攻击 1：提前保存引用
const chat = tsukiro.model.chat;      // 授权时保存
// …用户撤销授权后…
await chat({ messages });             // 仍然能调

// 攻击 2：拿原型上的方法
const fn = Object.getPrototypeOf(tsukiro.model).chat;

// 攻击 3：通过 Bridge 底层通道自行构造消息
//（如果 Bridge 不是宿主验证的，就能直接发原始 RPC）
```

即使插件**没有恶意**，这些模式也可能因第三方库缓存而意外绕过。

因此：**接口注入只做「尽力而为的便利层」**（让插件拿到的错误更早），**真正的校验必须在宿主侧的 Gatekeeper 里对每条 RPC 重做一遍**。

```
插件调用
  └─▶ Bridge 收到原始 RPC
        └─▶ ⛨ Gatekeeper.check(pluginId, permission)   ← 唯一的权威判定
              ├─ 通过 → 执行原语 → 写审计
              └─ 拒绝 → 返回 PERMISSION_DENIED → 写审计
```

## 2. 权限分级

| 级别 | 标识 | 授权时机 | 适用 |
|---|---|---|---|
| **安装时授权** | `install` | 安装时一次性弹窗 | 绝大多数权限（默认） |
| **每次确认** | `confirm` | 每次调用前弹原生确认框 | 极高风险：无障碍、截屏、录屏、发短信、拨号 |
| **禁止** | `denied` | 永不授权 | 宿主保留，插件申请即安装失败 |

`confirm` 级权限在 manifest 里正常声明，但安装弹窗必须**单独高亮**，明确告知「此权限每次使用都会再次询问」。用户若不同意该项，可选择**不安装**或**安装但不授予**（插件须能降级运行 —— 见 §6）。

### 2.1 `confirm` 级权限清单（完整）

| 权限 | 为什么这么危险 |
|---|---|
| `a11y` | 可读取屏幕上的一切，可模拟点击其他 App，等价于远程控制 |
| `screen.capture` | 可截屏，可能截到聊天记录、密码、验证码 |
| `screen.record` | 同上，且是持续性 |
| `sms.send` | 可经用户手机号发短信，涉及资费与诈骗风险 |
| `call.make` | 可拨号 |
| `notification.read` | 可读取所有通知，含验证码 |
| `contact.read` | 通讯录是高度敏感个人信息 |
| `sms.read` | 短信含验证码与私人通信 |
| `media.read`（全量相册） | 相册含私人照片 |
| `location` | 精确位置 |
| `message.read` | 可读取全部历史对话内容 |
| `sys.intervene` | 可打断用户当前操作、锁定应用、盖住屏幕 |
| `sys.clipboard.read` | 剪贴板常年装着密码与验证码 |

> **原则**：凡是「读别人的数据」「代替用户对外发消息」「打断用户当前在干的事」的，一律 `confirm`。

## 3. 权限清单（完整目录）

风险级别列：`install` / `confirm` / `—`（无需权限）。

### 3.1 文件与存储

| 权限 | 级别 | 说明 |
|---|---|---|
| `fs.read` | `install` | 读沙箱内文件（**沙箱内**，不能读系统文件） |
| `fs.write` | `install` | 写沙箱内文件 |
| `fs.delete` | `install` | 删沙箱内文件 |

> `fs.*` 只是 `install` 级，因为它被沙箱路径限制死了。真正的风险源是「越过沙箱」—— 而那是漏洞而非权限问题。

### 3.2 系统信息

| 权限 | 级别 | 说明 |
|---|---|---|
| `sys.time` | `install` | 读当前时间 |
| `sys.info` | `install` | 电量、网络状态、设备型号、语言区域 |
| `sys.clipboard.read` | `confirm` | 读剪贴板（常含密码、地址） |
| `sys.clipboard.write` | `install` | 写剪贴板、震动 |

### 3.3 媒体

| 权限 | 级别 |
|---|---|
| `media.read` | `confirm` |
| `media.camera` | `confirm` |
| `media.microphone` | `confirm` |

### 3.4 通讯

| 权限 | 级别 |
|---|---|
| `contact.read` | `confirm` |
| `sms.read` | `confirm` |
| `sms.send` | `confirm` |
| `call.make` | `confirm` |

### 3.5 日历与应用

| 权限 | 级别 |
|---|---|
| `calendar.read` | `install` |
| `calendar.write` | `install` |
| `app.read` | `install` |
| `app.launch` | `install` |

### 3.6 通知与定位

| 权限 | 级别 |
|---|---|
| `notification.send` | `install` |
| `notification.read` | `confirm` |
| `location` | `confirm` |

### 3.7 网络

| 权限 | 级别 | 说明 |
|---|---|---|
| `net` | `install` | 发起网络请求，**且**必须同时命中 `network.allow` 白名单 |

> `net` 本身是 `install` 级，但**白名单是权限的一部分**。`network.allow` 里的域名在安装弹窗中必须逐条列出，让用户知道数据会发到哪里。空 `allow` 数组 = 完全禁止网络。

### 3.8 UI

| 权限 | 级别 |
|---|---|
| `ui` | `install` |
| `ui.overlay` | `install` |

### 3.9 模型

| 权限 | 级别 | 说明 |
|---|---|---|
| `model.chat` | `install` | 调用模型。**消耗用户点数**，安装弹窗必须提示 |

### 3.10 上下文与消息

这一组是「插件影响 AI 说什么」的能力，风险在于**持续性与隐蔽性** ——
一次注入看不出问题，持续注入可以慢慢把 AI 的设定带偏。因此拆得比别处细。

| 权限 | 级别 | 说明 |
|---|---|---|
| `context.write` | `install` | 往上下文注入文本 / 追加消息。可撤销、有长度上限、记审计 |
| `context.hook` | `install` | 注册钩子（`onBuild` / `onBeforeModel` / `onAfterModel`）。**持续性影响**，比单次注入更高一档 |
| `message.read` | `confirm` | 读取消息内容（含历史对话） |
| `message.write` | `install` | 修改 / 删除已有消息 |
| `message.send` | `install` | **主动发消息，会触发模型调用、消耗点数**。安装弹窗必须提示 |

> **为什么 `context.write` 与 `context.hook` 分开**：前者是「我说一句」，后者是「以后每轮我都能插话」。
> 后者给用户的控制感更弱，理应让用户在安装时看得更清楚。
>
> **为什么 `message.send` 不并为 `model.chat`**：调模型是「用户问、AI 答」，
> 主动发消息是「插件替 AI 说话」。后者更容易被用来制造「AI 自己找我说话了」的假象，
> 因此单独列出，让用户在安装时明确知道。

### 3.11 调度

| 权限 | 级别 | 说明 |
|---|---|---|
| `schedule` | `install` | 创建后台定时任务 |

**关键约束**：任务**每次触发时重新校验权限**，而不是创建时校验一次。
用户在任务创建后撤销了 `model.chat`，那么定时任务里调模型一样会失败。
否则调度就成了绕过权限的通道。另外还有最短周期 60 秒、单插件最多 16 个任务、休眠不补跑。

### 3.12 系统干预（`confirm`）

| 权限 | 级别 | 说明 |
|---|---|---|
| `sys.intervene` | `confirm` | 屏幕拉回 / 锁定应用 / 弹出系统弹窗。**打断用户当前操作** |
| `sys.overlay` | `install` | 显示悬浮层。仅叠加显示，不打断 |

> 五个高敏感原语合并为一个 `sys.intervene`，理由见 `docs/05-primitives.md` §3.2.1。

### 3.13 高风险（`confirm`）

| 权限 | 级别 |
|---|---|
| `a11y` | `confirm` |
| `screen.capture` | `confirm` |
| `screen.record` | `confirm` |
| `mcp` | `install`（预留） |

### 3.14 无需权限

`state.*` · `crypto.*` · `tool.*` · `event.*` · `log.*` · `ui.toast`（含在 `ui` 内）

> 无需权限的原因：它们要么只操作插件私有数据，要么是纯计算，要么是基础设施。注意 `ui.toast` 归入 `ui` 权限组，因为往宿主界面弹东西也是一种 UI 侵入。
>
> **`context.*` 和 `message.*` / `schedule.*` 都不在这里** —— 它们影响的是 AI 说什么、
> 对话长什么样、后台什么时候干活，全部需要显式授权。

## 4. 安装时授权流程

```
用户选择 zip
   │
   ├─ 解析 manifest → 得到 permissions[] + reasons + network.allow
   │
   ├─ 检查是否有 denied 级权限
   │     └─ 有 → 直接拒绝安装，提示「该插件申请了不被允许的权限：xxx」
   │
   ├─ 构建授权弹窗（原生，不是 WebView，插件无法伪造）
   │     ┌────────────────────────────────────────────┐
   │     │  安装「时间插件」dev.tsukiro.time v1.0.0     │
   │     │  作者：Tsukiro                              │
   │     │                                            │
   │     │  该插件申请以下权限：                        │
   │     │                                            │
   │     │  ▸ 读取系统时间            sys.time         │
   │     │    用途：读取系统时间以回答时间问题            │
   │     │                                            │
   │     │  ⚠ 调用 AI 模型（会消耗你的点数） model.chat │
   │     │    用途：翻译内容                             │
   │     │    ┌──────────────────────────────────┐   │
   │     │    │ ⚠ 每次使用都会再次询问             │   │  ← confirm 级
   │     │    └──────────────────────────────────┘   │
   │     │                                            │
   │     │  网络访问：api.example.com                  │
   │     │                                            │
   │     │      [ 取消 ]        [ 同意并安装 ]         │
   │     └────────────────────────────────────────────┘
   │
   ├─ 用户点「同意并安装」
   │     ├─ 记录授权：grants[pluginId] = { perm: { grantedAt, level } }
   │     ├─ 解压到沙箱
   │     └─ 注册注册表 → 触发 UI 刷新
   │
   └─ 用户点「取消」
         └─ 中止，磁盘无残留（因为此时还没解压）
```

**顺序很重要**：权限弹窗必须在**解压之前**。这样拒绝时不需要清理磁盘，也不存在「先落地再删」的竞态。

## 5. 运行时校验

### 5.1 校验点

```dart
// packages/plugin_core/lib/src/permission/gatekeeper.dart
class Gatekeeper {
  CheckResult check(String pluginId, Permission perm, {String? toolName}) {
    // 1. 插件是否已安装且启用
    // 2. 该权限是否在 manifest 中声明（没声明就直接拒，不能"临时申请"）
    // 3. manifest 声明的级别是否为 denied
    // 4. 用户是否已授予
    // 5. confirm 级 → 触发确认流程（异步）
    // 全部通过 → allow
  }
}
```

**第 2 步是关键**：插件不能调用 manifest 里没声明的权限，即使那个权限用户已经授予了别的插件。这叫**声明即上限**。

### 5.2 confirm 级权限的调用时序

```
插件: await tsukiro.sms.send({ to, text })
  │
  ├─ Bridge → Gatekeeper.check(pluginId, 'sms.send')
  │     └─ level == confirm
  ├─ 宿主弹原生确认框（含插件名、具体参数预览：收件人 + 内容）
  │     ┌────────────────────────────────────┐
  │     │  「短信助手」想要发送短信            │
  │     │  收件人：138****8888                │
  │     │  内容：您的验证码是 4821            │
  │     │                                    │
  │     │  [ 拒绝 ]      [ 允许这一次 ]        │
  │     └────────────────────────────────────┘
  ├─ 用户拒绝 → 返回 USER_CANCELLED（不是 PERMISSION_DENIED，以便插件区分语义）
  ├─ 用户允许 → 执行 → 审计（含参数快照）
  └─ 注意：不提供「总是允许」选项
```

**`confirm` 级永不提供「不再询问」**。这是硬规则。

### 5.3 限流（宿主侧硬限制）

| 限制项 | 默认值 | 超出行为 |
|---|---|---|
| `model.chat` 调用频率 | 30 次/分钟/插件 | `RATE_LIMITED` |
| `model.chat` token 消耗 | 由用户点数余额决定 | 余额不足 → 提示，不静默失败 |
| `net.*` 请求频率 | manifest 的 `maxRequestsPerMinute`，默认 60 | `RATE_LIMITED` |
| `log.*` 写入 | 100 条/分钟 | 丢弃 + 记一次限流 |
| `state.*` 容量 | 5 MB/插件 | `IO_ERROR` |
| `ui.*` 弹窗 | 1 个并发/插件 | 后者排队 |
| `notification.send` | 10 条/分钟 | `RATE_LIMITED` |

> 这些限制**不在 manifest 里可配**（除了 `maxRequestsPerMinute` 只能调低不能调高）。目的是防止插件把用户的点数或注意力刷爆。

## 6. 权限撤销

### 6.1 用户界面

```
设置 → 插件 → 时间插件 → 权限
  ┌────────────────────────────────────────┐
  │ 读取系统时间          sys.time          │
  │ ▸ 用途：读取系统时间以回答时间问题        │
  │                        [ 已授权 ●─── ]  │  ← 可切换
  │                                        │
  │ 调用 AI 模型          model.chat        │
  │ ▸ 用途：翻译内容                         │
  │                        [ 已授权 ●─── ]  │
  └────────────────────────────────────────┘
  撤销后该插件相关功能会立即停止工作。
```

### 6.2 撤销后的行为

| 时机 | 行为 |
|---|---|
| 立即 | `Gatekeeper` 的授权表更新（内存 + 持久化） |
| 下一次调用 | 返回 `PERMISSION_REVOKED` |
| 事件通知 | 向插件发 `permission.change` 事件，让插件有机会优雅降级 |
| UI | 依赖该权限的插槽控件自动隐藏（若 `provides.ui[].permissions` 已声明） |
| 审计 | 记录 `permission.revoke` |

**不自动卸载插件**，也不自动停用 —— 由插件自己决定降级还是报错。

### 6.3 撤销 `model.chat` 的特殊处理

`model.chat` 被撤销后，插件无法再调模型。但已在进行中的流式调用**不中断**（避免用户看到半句话），流结束后不再允许新调用。

## 7. 审计日志

### 7.1 记录内容

```jsonc
{
  "id": "audit_01HXYZ...",
  "ts": "2026-02-14T10:23:41.512+08:00",
  "pluginId": "dev.tsukiro.time",
  "pluginVersion": "1.0.0",
  "kind": "primitive",              // primitive | permission | plugin | network
  "primitive": "sys.time",
  "permission": "sys.time",
  "argsDigest": { "tz": "Asia/Shanghai" },   // 脱敏后的参数摘要
  "result": "ok",                   // ok | denied | error
  "errorCode": null,
  "durationMs": 3,
  "bytesIn": null,
  "bytesOut": 96
}
```

### 7.2 脱敏规则（必须在写入前执行）

| 原语 | 脱敏方式 |
|---|---|
| `fs.read` / `fs.write` | 只记路径，**不记内容** |
| `model.chat` | 只记消息条数 + token 估算，**不记内容** |
| `sms.send` / `sms.read` | 手机号保留前 3 后 4，正文只记长度 |
| `contact.*` | 只记条数，不记姓名电话 |
| `location.*` | 坐标降到 2 位小数（约 1km 精度） |
| `sys.clipboard.*` | 只记长度 |
| `net.*` | 记域名 + 状态码，不记 body |
| `crypto.*` | 只记算法名，**绝不记密钥** |

> 脱敏在 `plugin_core/audit` 里做，**在写数据库之前**。日志本身不能成为泄密渠道。

### 7.3 保留与清理

- 默认保留 **30 天**，滚动删除。
- 用户可在设置里「清空审计日志」。
- 单插件日志占用上限 **2 MB**，超出按时间淘汰。

### 7.4 用户可见性

设置 → 隐私 → 插件活动记录，按插件分组展示：

```
时间插件
  今天 10:23  读取系统时间              3ms     ✓
  今天 10:25  调用 AI 模型（1 条消息）   842ms   ✓
  今天 10:31  读取系统时间              2ms     ✓
翻译插件
  今天 10:28  读取剪贴板                1ms     ⛔ 已拒绝（未授权）
```

**「已拒绝」必须显示**。让用户看到插件在尝试什么，这本身就是一种防护。

## 8. 特殊情况

### 8.1 权限升级（插件更新后申请新权限）

```
插件从 1.0.0 升到 1.1.0，新增 media.read 权限
  ├─ 不自动继承旧授权
  ├─ 弹增量授权窗：「时间插件更新后申请了新权限：读取相册」
  ├─ 同意 → 更新授权，升级完成
  └─ 拒绝 → 升级取消，保留旧版本（不破坏已装版本）
```

### 8.2 插件声明了但从不使用的权限

不做强制，但**商店审核时降级/拒收**。安装弹窗中过度申请权限是明显的坏信号，用户会看到。

### 8.3 宿主自身能力的权限

宿主自己调系统 API 不需要走 Gatekeeper（它是守门人本身）。但宿主的调用**同样写审计**，只是 `pluginId` 记为 `__host__`，便于统一排查。

### 8.4 系统权限与插件权限的关系

**两层，不要混淆**：

```
第 1 层：系统权限（Android/iOS 层面）
  media.read → 需要 READ_MEDIA_IMAGES
  宿主统一申请，用户拒绝后宿主拿到空结果

第 2 层：插件权限（本文件描述的）
  插件 media.read → 宿主判断是否授予该插件

顺序：Gatekeeper 通过 → 检查系统权限 → 缺失则触发宿主级系统权限申请 → 用户同意 → 执行
```

即：**系统权限由宿主统一持有，插件权限是二次分发**。某个插件被撤销相册权限，不影响宿主的系统权限，也不影响其他插件。
