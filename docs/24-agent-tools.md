# 24 · 宿主工具（Agent 自己的工具）

> 状态：设计定稿，待实现
> 相关：`docs/05-primitives.md`、`docs/06-permissions.md`、`docs/17-agent-loop.md`

---

## 1. 问题：宿主工具不是一等公民

Agent 现在能调用工具，但**工具只能来自插件**。

```dart
// ToolRegistry 的唯一注册入口
List<ToolNameConflict> registerPlugin(PluginManifest manifest)
```

```dart
// AgentLoop 的分派
outcome = await invokeTool(tool.pluginId, tool.handler, call.arguments);
```

`RegisteredTool` 的 owner 是 `pluginId`，而宿主没有位置。

后果：**"让 AI 读写文件"这件事无法通过注册工具实现。** 要么塞进某个插件（错，见 §5），要么绕开门禁（更错）。

---

## 2. 为什么会写成这样（根因，比结论重要）

这不是谁写错了。它是**"第一个用例定义了形状"**的典型：

1. **项目是插件优先的。** 第一版的需求是"宿主 + 插件系统"，所以最先建的是插件内核：清单 → 声明 → 三张表。`registerPlugin(manifest)` 是那个时刻**唯一自然**的接口——因为插件在清单里声明工具。

2. **AI 回路是后加的。** 它需要工具表，而当时**世界上唯一的工具来源就是那张由插件填的表**。所以 `AgentLoop(tools: toolRegistry)` 是唯一能写的接线。**没有人决定"工具只能来自插件"，只是第二个来源从未出现过。**

3. **`__host__` 这个标识诞生的位置不对。** 审计层需要"谁在花钱"，于是约定宿主调用记 `pluginId = '__host__'`。但审计关心的是**记账**，权限关心的是**能不能做**——两件事。这个标识只实现了一半：

   ```
   审计层：认 __host__      ✓
   权限层：不认 __host__    ✗  →  fail-closed 会拒掉
   ```

   权限层比 AI 回路更早诞生，那时确实只有插件会调东西。

4. **两层命名空间容不下第三个来源。** 工具表的键是 `name`，owner 是 `pluginId`，这是 `plugin → tool` 的两层结构。宿主不是插件，所以**没有地方放它**。而"工具必须有 owner"这个假设从来没被写出来过——**没写出来的假设，不会有人去检查它**。

### 可迁移的教训

这个仓库里同类的例子不止一个：

| 现象 | 第一个用例留下的约束 |
|---|---|
| 工具只能来自插件 | 第一个工具来源是插件清单 |
| 安装只能 `installFromAssets` | 第一个需求是装演示插件 |
| `fs.*` 声明了 7 个，一个跑不起来 | 第一个调用方（插件）一直没出现 |
| 插槽白名单 | 第一个插槽是宿主自己定的 |

**规律：第一版实现的约束，会静默变成架构约束。**
对策不是"写得更小心"，而是**在加第二个用例时，先问一句"这个模块的隐式假设是什么"**。

## 3. 设计决定

> **宿主是工具的合法来源之一，和插件平级。**

三条推论：

1. **工具表的 owner 从 `pluginId` 推广为"来源"** —— 不允许是 null，也不允许用空串。
2. **门禁认 `__host__`** —— 但**不是放行所有权限**：宿主工具自己声明所需权限，仍然过 `gatekeeper.check`。区别只在于"宿主这个身份是已知的"，而不是"宿主免检"。
3. **分派按来源分流** —— `__host__` 走宿主本地实现，其余走插件运行时。

### 明确不做的事

- **不让宿主工具跳过门禁。** 跳过一次，整条权限链路就变成了"看情况"，而这套系统的价值恰恰是"每个能力都问过"。
- **不把文件工具做成插件原语。** 理由见 §5。

## 4. 三层改动

### 4.1 `ToolRegistry.registerHostTool`

```dart
/// 注册一个属于宿主的工具。
///
/// 和 registerPlugin 并列，不是它的特例 —— 宿主不是插件，
/// 把宿主伪装成插件会让 manifest / permissions / 沙箱这些概念全都变形。
void registerHostTool(RegisteredTool tool);
```

约束：
- `tool.pluginId` 必须是 `__host__`（断言，不是约定）
- 名字冲突规则与插件工具一致：不能覆盖已存在的工具
- `pluginVersion` 用宿主版本

### 4.2 `Gatekeeper` 认 `__host__`

现状：`check('__host__', perm)` 走"未知插件 → 拒绝"。

改动：`__host__` 视为**已授权自身声明过的一切权限**——但仍要把权限列出来（审计要用），且**不可撤销性要显式**：宿主工具是随应用发布的，用户不能"禁用"它，只能不用它。

> 这里要留一个口子：将来如果有"宿主工具总开关"（比如"允许 AI 操作文件"），
> 它应该是 `HostPreferences` 里的一项，在 `check` 之前判，而不是塞进门禁的静态表。
> 门禁管"这个身份有没有这个权限"，偏好管"用户现在想不想用它"。

### 4.3 `chat_controller` 分派

```dart
invokeTool: (pluginId, handler, args) {
  if (pluginId == '__host__') return _hostTools.execute(handler, args);
  return pluginHost.invokeTool(pluginId, handler, args);
}
```

`_hostTools` 是一个 `Map<String, Future<Object?> Function(Map<String,dynamic>)>`。

## 5. 为什么文件工具不能是插件原语

这是本设计里最重要的一条边界。

| | 宿主工具 | 插件原语 |
|---|---|---|
| 用户信任的是 | **这个应用** | **每一个装的插件** |
| 授权 | 一次，针对"这个智能体" | 每插件 × 每权限 |
| 装新插件 | 不影响已有授权 | **可能扩大攻击面** |

如果文件工具进原语目录，那么"装一个插件"就等于"可能给它用户的文件"。

而且有个更具体的安全问题——**权限洗白**：

```
插件 A（无文件权限）
  → 写插件 B 到 plugins/
  → B 申请文件权限
  → 用户批准 B
  → A 通过 B 拿到了文件访问
```

**同一个原则适用于 `exec`：有能力改变宿主的东西，必须是宿主能力。**

## 6. 第一批宿主工具

| 工具 | 参数 | 说明 |
|---|---|---|
| `list_files` | `path`（相对工作区根） | 列目录，目录在前 |
| `read_file` | `path` | 读文本；二进制返回明确错误而不是乱码 |
| `write_file` | `path`, `text` | 写文本；父目录自动建 |
| `delete_file` | `path`, `recursive` | **需要确认**（见 §7） |

全部落在**当前智能体的工作区**里（`<app>/workspaces/<agentId>/`），路径过 `SandboxPathGuard`。

### 不做 `exec`

| 路线 | 机制 | 需要什么 |
|---|---|---|
| Shizuku | ADB 授权，进程以 `shell` UID 运行 | 用户一次性 ADB 授权 |
| PRoot | 用户态 Linux | 打包 rootfs（几十 MB） |
| Termux + MCP | 独立 app | 用户另装 |

**三条都需要用户显式授权一次**，没有一条是"应用自带"。而且 Android 上没有 POSIX 环境，真实用途有限。

`exec` 是一次独立的决定，不和工作区混在一起做。

---

## 7. 危险操作

`delete_file` 和将来的 `write_file` 覆盖是**不可逆**的。

现状：`PermissionLevel.confirm` 已存在（"每次确认、永不不再询问"），但**没有 UI 流程**。

第一批做法：
- `write_file` 只允许**新建**，覆盖已存在文件返回 `CONFLICT`，让模型换名字或先读
- `delete_file` 走 `confirm` 级权限
- 真正的确认 UI 单独做

> 这不是最终方案，是"先不给自己造一个静默删文件的能力"。

---

## 8. 验证清单

实现后必须验证：

1. 宿主工具出现在 `toOpenAiTools()` 里（单测）
2. 宿主工具能被分派执行（单测）
3. 插件工具**仍然**受门禁管（单测，防止改动放开了所有人的权限）
4. 未知 `pluginId` 仍然被拒（单测，fail-closed 没退化）
5. 真机：让 AI 在工作区建文件 → 在工作区页看到
6. 真机：让 AI 读一个不存在的文件 → 得到明确错误，不是崩溃

第 3、4 条是**防退化测试**——加一个"放行宿主"的改动，最容易顺手把"放行所有人"也带进来。
